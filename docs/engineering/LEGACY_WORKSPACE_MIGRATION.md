# Legacy workspace migration: identity and acceptance boundaries

The legacy workspace backup (`business-suite/v1`) is not a Go station backup. The legacy organization is `org_<demo_session_id>` and the station organization is `org_test_<suite_demo_space>`. These cookies have different formats and neither value establishes authorization for the other system. Never infer an organization mapping from matching browser sessions or import data automatically.

A migration must require an explicit export from the legacy workspace and an authenticated station administrator selecting the destination workspace. Treat the file as untrusted. Before any destination write, validate its complete table and column manifest, source organization on every row, types, duplicate IDs, business invariants and cross-table references. Reject unknown schemas rather than silently dropping data. Show the source, destination, row counts, conflicts and unmapped identities before committing. The destination must be backed up first; import must be atomic, auditable and repeat-safe, with no partial success. Never replace existing destination records implicitly.

The legacy export deliberately excludes users, memberships, audit events, idempotency keys, outbox events and seed state. These cannot be reconstructed from the export. Historical audit and pending integration delivery require separate explicit handling; importing business rows must not claim those records were migrated. Existing sessions and grants must not be overwritten. References to legacy identities require explicit mapping to destination accounts or a clearly preserved historical identity; never map all operators to an administrator.

Fields requiring identity review include CRM account, activity and opportunity `owner_id`; POS shift and sale `cashier_id`, held cart `locked_by`; and shop cart, order and review `user_id`, plus reservation `session_id` (the legacy checkout stores `context.userId` there). Additional migrations and business tables must be scanned for other identity references. Active held-cart locks and open transactions need an explicit policy; blindly retaining a legacy lock can make a cart unusable.

Acceptance requires a real exported multi-table workspace with linked transactions, non-default accounts, live and historical records; verify counts, amounts, stock balances and referential integrity after migration, tenant isolation, front/back and owner visibility, duplicate import behavior, rollback on invalid data or interruption, and unchanged destination data on rejection. Compare the result against the actual source, not fixtures alone. Until these checks pass there is no supported import or public cutover based on it.
