# MES 成品與 ERP 庫存整合

## 架構文件

影響系統：ForgeFlow MES 與 LedgerWorks ERP。MES 成品入庫保留批次追溯，並在相同 SQLite 交易新增版本化 `mes.finished_goods.received` outbox 事件；ERP 消費者以獨立交易過帳庫存。管理員可查看待處理、已過帳和失敗原因並重試；MES 已入庫不代表 ERP 已過帳。事件具有穩定 event ID、租戶、來源收貨 ID、批次、MES 商品、數量、時間及 schema 版本。重試不得重複過帳。既有未產生事件的歷史入庫必須以可審核的補送工作流程處理，不能自動推定已同步。

MES 商品與 ERP 品項為不同主檔，SKU 非唯一可靠鍵。管理員須建立租戶內明確的 MES 商品 ID 到 ERP 品項 ID 對應；SKU 與單位只供確認。還需明確選定同租戶有效的 ERP 成品倉庫，保存於事件或版本化設定，後續變更不得改寫過去事件的目的地。單位不同的情況一律停留待處理，直到有明確可稽核的轉換規則。MES 尚無完工成本，ERP 帳本所需成本必須由有權限的管理員確認並記錄依據；不可靜默以零或猜測成本過帳。

## 程式邊界

- 操作者須經受影響站台的適當授權；所有查詢、映射、事件與過帳皆限定同租戶，不接受跨租戶商品、品項或倉庫。
- MES 本地事務原子提交成品收貨、庫存、稽核、冪等紀錄和 outbox；交易失敗時不得留下事件或部分庫存。並行及同鍵重試不得重複建立事件。
- ERP 消費者驗證事件版本、品項、倉庫、單位、成本及整數溢位；以事件 ID 建立唯一消費紀錄，與 ERP stock ledger、成本及稽核同一交易提交。失敗可重試並保留原因；不得丟失、重複或跨租戶過帳。
- 未建立映射、目的地失效、缺成本或單位不符時顯示明確待處理狀態，不能回報已同步；管理員修正後可安全補送。歷史或失敗事件不可因映射變更悄悄轉往其他品項。
- ERP 既有採購入庫與成本規則不得被旁路或破壞；新帳本類型、估值及權限須有明確審查與測試。管理介面以實際事件及過帳資料呈現，不模擬已同步。

## 測試計畫

先寫隔離資料庫與遠端 CI 測試：MES 入庫事件原子性與失敗回滾；相同與不同冪等鍵重試；同事件並行消費只建立一次帳本；同租戶映射、錯誤租戶、停用品項/倉庫、缺映射、成本及單位差異；故意中斷與恢復；帳本餘額、成本與稽核一致；映射變更不改寫既有事件；舊收貨補送與重複補送。再接管理介面與實際瀏覽器驗收。本地不執行測試。

## 現況

MES 入庫已加入待驗證事件，ERP 有獨立 stock ledger 與 costing。事件尚未由 ERP 過帳；映射、過帳、補送及操作畫面需依各迭代的實際程式與驗證狀態判定。

收貨事件的 MES 商品 ID 必須於收貨交易內再次查證屬於同一租戶，歷史工單若指向不存在或跨租戶的商品應拒絕，且不可留下庫存、收貨或事件。事件 `eventId` 必須與 outbox 識別碼一致，重試回傳相同識別碼。映射、目的地與成本尚未確定時，事件只能視為待配置來源；後續過帳前須固定經確認的目的地與成本，不能以目前最新設定默默重新導向。

## 商品與倉庫映射命令

在 ERP 後台新增管理員命令 `POST /api/stations/erp/mes-integration`，`action=mapProduct` 指定 `mesProductId`、`erpItemId`、`warehouseId` 與冪等鍵。操作人須同時具有同租戶啟用中的 MES 和 ERP 後台管理員權限，並在寫入交易內重查；需驗證 MES 商品存在且 active、ERP 品項及倉庫有效且同租戶、兩邊單位完全相同。任何條件失敗不寫映射、稽核或冪等紀錄。

採附加式版本紀錄：同租戶每個 MES 商品最多一個 active 映射；更換映射將舊紀錄停用並新增新紀錄，兩者和稽核同一交易。相同冪等鍵及內容回傳原結果，內容不同拒絕；不同商品可各自映射。建立映射不回填舊事件、不執行 ERP 過帳，也不推定成本。ERP 管理介面列出同租戶映射版本及有效狀態。

測試先行：建立、同鍵重試、不同內容重用鍵、更新版本、跨租戶與無效品項/倉庫、單位差異、MES 或 ERP 管理員權限撤銷、資料庫寫入失敗的全交易回滾，以及並行更新時唯一 active 映射。收貨事件與映射綁定、成本確認、過帳與補送屬後續獨立迭代。

收貨事件測試 Red：[遠端完整 Go race 紀錄](https://github.com/Davis1233798/profolio/actions/runs/41479964312/job/125395343565) 顯示成功收貨後找不到事件；後續已新增交易內事件，Green 仍待最新版本 CI。版本化商品映射 API 及 migration 已實作，ERP 管理介面、事件與映射綁定、成本確認及過帳仍待完成。

## 管理員確認成品入帳

ERP 後台另提供 `POST /api/stations/erp/mes-receipt`，輸入 `eventId`、當前 active `mappingId`、明確確認的整數 `unitCost`、成本依據 `reason` 與冪等鍵。成本允許零但必須有非空原因；數值與成本總額遵循採購入庫既有上限。操作者須在交易內重驗同租戶 MES/ERP 後台管理員權限。

交易讀取同租戶 pending 的 MES 成品收貨事件，解析並核對 event ID、schema、組織、MES 收貨、批次、商品和數量與現有資料一致；映射須 active 且對應相同商品，商品、ERP 品項及倉庫仍須有效且單位相同。寫入不可變的 ERP 成品過帳紀錄（保存事件、來源收貨、映射版本、品項、倉庫、數量、單位成本與原因），以組織加事件 ID 唯一約束去重。依現有 ERP ledger 最新餘額和 costing 規則計算庫存、總成本與移動平均，再同交易寫帳本、costing、處理紀錄、稽核、冪等結果並將事件標記 processed。成功回傳處理與帳本識別碼。

相同冪等鍵及內容回傳相同結果；同事件使用另一鍵不可再次過帳。其他租戶事件、過期或異商品映射、缺少成本原因、無效金額、異常事件內容、狀態不符與撤銷授權均拒絕且不部分寫入。事件缺映射或成本時保留 pending，由管理員明確選擇與確認；映射一旦過帳即保存該版本，之後更改不追溯。故障時整筆回滾並可安全重試。歷史 MES 收貨的補送另行設計，不能把缺少事件當作已同步。

先在遠端 CI 寫測試：完整 MES 收貨→映射→ERP 過帳、同鍵與不同鍵重試、跨租戶與錯誤映射、成本邊界、撤銷權限、故障注入回滾，以及並行處理同一事件只能產生一筆帳本與成本變更。
