# MES：品檢放行、成品入庫與工單結案

## 架構文件

系統：ForgeFlow MES，延續 [SAP 工作台範本](../design/sites/mes.md)。目前 Go 工作站在報工達到目標後將工單標為 `completed`，品檢只記錄抽樣結果，尚無成品入庫與結案流程。新增獨立成品批次與庫存過帳紀錄，維持報工紀錄、品檢結果、入庫與工單間的可追溯關聯；在同一租戶交易中驗證品質、數量及狀態，最後提交庫存、狀態、重試紀錄和稽核。

批次建立、品質處置、入庫及結案均需後台管理員；非管理員畫面可查看資料，但不應提供可提交而必定遭 403 拒絕的批次建立操作。後端仍獨立執行權限檢查。

`completed` 表示報工完成，並不表示成品可用；`closed` 代表已完成品質處置與入庫。畫面在 MES 後台提供批次明細、品質處置與入庫／結案操作，依角色權限顯示，錯誤或未完成條件以文字呈現。資料來自 API，不以靜態數字取代。

## 程式邊界

- 每個成品批次必須歸屬相同組織的工單及生產報工；累計批次數量不得超過該報工良品數，報廢數不得入庫。入庫及品質處置數量以整數計算，不可負數或超額。
- 明確區分待檢、隔離、放行與已入庫；抽樣品檢紀錄本身不自動代表整批放行。未明確放行或處於隔離／重工的數量不可計入可用成品庫存。放行、隔離處置及結案由後台授權角色執行。
- 只有報工完成且所有良品均有可追溯批次、每批已完成品質處置且放行量已入庫、隔離或報廢量有明確處理時才能結案。歷史資料不能因部署而被自動放行或補入庫。
- 全數報廢且良品為零的已完成工單，在已報工總量符合目標、沒有未處置成品批次時可結案；不得憑空建立零數量入庫。測試須走實際開工與報工 API，並確認結案不產生庫存。
- 重試鍵與請求內容綁定；相同請求重送僅一次，異內容重用拒絕。跨組織批次、無權身分、重複入庫及競態更新必須拒絕或安全重試；失敗不得留下部分庫存或稽核。
- MES 成品庫為本系統獨立帳本，與 ERP 中央庫存同步尚未完成，畫面不得聲稱跨系統已同步。新 schema 必須以版本化遷移加入，保留既有資料與備份相容策略。

## 程式測試計畫

先在隔離資料庫撰寫 Red：完整報工→建批→品檢→放行→入庫→結案；待檢／隔離不得入庫，未處置或數量不符不得結案；不合格不可直接放行；重送及並行入庫只記一次；超量、跨租戶、無權角色及交易中斷回滾；既有 `completed` 工單不被自動放行。另驗證前端角色、載入／錯誤狀態及行動寬度。Linux／Windows 遠端 CI 與瀏覽器驗收，不在本機執行測試。

## 批次歷史顯示

畫面以站台資料 API 的租戶隔離 `finishedGoodsBatches`、`finishedGoodsQualityDispositions` 和 `finishedGoodsInventory` 為資料來源，依批次 ID 關聯處置及庫存；重整後應保留選取與可執行動作所需狀態。既有資料載入上限需明示；使用者以目前身分只能操作 API 授權的資料。先新增以真實回應形狀驗證資料轉換的測試，涵蓋空資料、待檢、放行、已入庫及多批次隔離，再調整 UI，不使用僅存於頁面記憶體的批次資料。

批次重工回到待檢後，不得把先前隔離紀錄的數量呈現為目前檢驗結果；重檢選項與輸入應重新確認。已放行／入庫批次使用放行紀錄，已隔離批次使用隔離紀錄；資料不完整時顯示缺失而不推測數量。先以待檢重工批次搭配舊隔離紀錄撰寫測試，再修改顯示邏輯。

## 隔離品處置

隔離批次需由後台管理員以 `resolveQuarantine` 明確選擇整批重工或報廢，提供原因並保留新的品質處置紀錄及稽核。重工將批次送回待檢，須重新執行品質處置，不能直接入庫；報廢將批次標記為 `scrapped`，不可入庫，但其數量視為已處理以供工單結案核算。不得修改原始報工數或舊品質紀錄。操作以批次全量為單位，不支援部分重工與部分報廢；錯誤狀態、空原因、重送不同內容、跨租戶或無權角色均拒絕。結案須確認已入庫與明確報廢的批次數量相加等於工單良品量，且無待檢／隔離批次。

品質檢驗數量與後續處置數量屬於不同事件，不得把「整批送重工」再記為全批檢驗不合格。新增獨立處置事件表，保存同租戶批次、處置方式、整批處置數、原因與重檢順序；原品質處置表只保存實際檢驗分配。重工的重檢下界由處置事件讀取。保留既有歷史資料，不自動刪除或重新解讀早期紀錄；統計須依事件類型區分。先測 100 件抽檢處置為 99 合格／1 不合格、整批重工後檢驗數量不變，以及整批報廢不進庫存，再實作。

批次詳情應顯示該批次的處置歷程（時間、重工或報廢、數量與原因），資料來自伺服器的租戶範圍 `finishedGoodsResolutions` 資料集；不得混入其他批次，也不得把處置數量標成檢驗不合格數。清單以伺服器已載入的資料為準並保留 500 筆上限提示。先測不同批次的歷程隔離與排序，再接入畫面。

先測隔離→重工→重新放行→入庫→結案、隔離→報廢→結案、重試／權限／跨租戶與異常狀態；檢查庫存不含報廢且原處置紀錄保留。此處置不代表實際設備重工或 ERP 庫存同步。

## 品檢紀錄關聯

品質處置必須明確引用相同租戶、工單及報工的 `mes_quality_checks` 紀錄，並保存該 ID 供稽核。放行需引用全數通過的品檢；隔離需引用含不合格數的品檢。抽樣結果仍不自動放行全批：管理員另行決定批次處置。重工後放行必須使用重工處置後新增的品檢，不能重用原不合格紀錄；時間相同時以資料庫紀錄順序判斷。無紀錄、錯誤報工、跨租戶、失敗品檢放行或重用重工前紀錄皆拒絕，保留原始紀錄且不過帳。先撰寫這些 API 測試，再實作與連結 UI；既有未關聯的歷史處置不自動補資料或改變庫存狀態。

引用的品檢必須同時符合狀態及數量：放行要求 `status=passed`、不合格數為零且通過數等於抽樣數；隔離要求 `status=quarantined` 且存在不合格數。內容矛盾的歷史紀錄不能被當作有效的放行證據。

建立品質檢查的 `operations` API 回傳 `qualityCheckId`；相同重試鍵必須回傳同一識別碼，供成品處置引用。測試使用正式 API 建立與報工關聯的品檢，再確認回傳 ID 與資料庫、重試結果一致，不以直接寫入假品檢取代端到端流程。

品質處置輸入的合格與不合格數都必須在 0 至 1,000,000 範圍內，再加總核對批次數量；加總不得因整數溢位而繞過限制。錯誤輸入不得建立處置、庫存或稽核紀錄。先以極大整數、負值及正常邊界撰寫 API 測試，再修正驗證。

操作畫面在切換工單時清除先前選擇的報工，並僅允許選取目前工單的報工以建立可追溯品檢；切換批次時清除先前選擇的品檢證據。伺服器仍需獨立驗證工單、報工及品檢的關聯，不以畫面篩選作為授權依據。測試需確認不同工單或批次間不沿用舊選擇。

## 舊版成品資料表升級

開發期間可能存在早期 `0006` 成品資料表，該表缺少後續新增的 `quality_check_id`、`reinspection_after` 或 `reason` 欄位；`CREATE TABLE IF NOT EXISTS` 不會補欄位。啟動時必須在既有 migration 交易內檢查資料表欄位，僅新增缺少欄位並保留所有舊紀錄；不可假裝歷史處置已有品檢證據。先以早期 schema 與實際資料建立遠端測試，驗證升級後資料保留、欄位預設、重啟可重複執行及失敗回滾，再實作。若缺少其他必要欄位或 schema 不相容，應明確失敗而非靜默覆蓋。

## 成品批次標籤

MES 後台列印中心提供成品批次標籤預覽，從現有租戶授權的 `finishedGoodsBatches` 資料集取得批次編號、工單、數量與狀態，條碼使用批次編號；預覽須保留待檢／隔離狀態，標籤不表示品質放行或已入庫。跨租戶 ID、前台帳號及未授權身分不得取得後台列印資料。先以 API 測試核對合法批次及越權／跨租戶拒絕，再接入標籤列印介面；遠端瀏覽器需驗證標籤與 Code128，實體印表機另行驗證。

既有資料可能含非 Code128 可列印 ASCII 字元，不能在列印時靜默產生錯誤條碼或使整個畫面崩潰。無法編碼時保留原文、顯示明確錯誤並停用列印；不可更改歷史編號或替換成不同識別碼。先測有效編號、空值、中文與控制字元，再接入共用標籤元件；最終還需實際瀏覽器與掃描器驗收。

重複產生同一筆標籤預覽時，條碼元件應重新檢查產生結果；新預覽未完成前列印維持停用，成功後可重新列印。編碼器失敗與不支援字元都應顯示一般性的產生失敗訊息，不能將其他錯誤誤判為字元問題。切換選項或預覽失敗時不得保留可列印的舊預覽。
