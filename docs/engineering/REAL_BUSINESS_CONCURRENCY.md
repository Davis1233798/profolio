# 真實業務 API 的隔離併發展示

## 架構與程式邊界

MES 與電商實際併發展示必須透過正式 Go 業務 API 與正式業務表；每次展示使用獨立臨時 SQLite 資料庫，建立隔離測試身分與虛構業務資料。不得在正式工作區資料庫建立無法清理的測試租戶，也不得將隔離 `traffic_records` 當成正式報工或訂單。正式展示功能須有可控的資料庫生命週期、明確授權、並行請求與最終業務表核對；模擬付款必須清楚標示。

第一輪先建立遠端 CI 的真實 API 交易證據：隔離檔案資料庫中，MES 管理員啟動工單，多個前台操作員請求競爭完整產量，核對工單上限、單筆報工與重試；電商對單件庫存併發 checkout，核對訂單、庫存與預留，同鍵重試不重複。請求使用正式登入、角色、租戶、API 與資料表，不藉由直接更新取代交易。測試結束由測試框架刪除臨時目錄；不得稱此為公開網路或多節點吞吐量驗證。

## 測試

先建立隔離組織，取得正式 API 工作單、工序和商品；對每個站點同時發送不同鍵的請求，核對成功數與衝突、正式資料表及冪等重試。確保另一租戶不受影響。遠端 GitHub CI 執行，不在使用者機器執行本機測試。後續仍需完成可安全操作、可觀測並可回收的後台展示介面及故障／逾時重試驗證。

## 可操作展示的資源與權限邊界

後台使用者只可啟動自己站台的展示；須在主站 API 驗證同租戶後台管理員與 Origin，並限制同時執行數、請求量及執行時間。伺服器生成執行識別碼及獨立臨時目錄，初始化獨立 SQLite 與 App；正式帳號、session 與 fixtures 只存在隔離資料庫。瀏覽器不得指定隔離資料庫路徑、使用者或租戶識別。內部併發器透過僅供程序內使用的受限 HTTP handler 發送正式登入及業務請求；不得公開隔離帳密或將隔離服務綁定公開網路。

執行階段需分別顯示準備、交易、核對、完成或失敗；最多 32 個請求，工作結束後等待所有在途交易，再查實際報工／工單或訂單／庫存／預留資料並回傳有界摘要。回應逾時的請求須標為未確認並以最終業務紀錄核對；不得將逾時直接計為交易失敗。關閉隔離 DB 後刪除僅由服務產生的專用目錄；清理失敗須回報，不刪除使用者指定的路徑。需限制併發執行與資源，並驗證程式異常結束後的遺留目錄處理。SQLite 單連線及模擬金流的限制須在 UI 說明。

開發順序：先測未授權拒絕、執行數限制、兩個隔離 run、正式業務 handler 與實表核對、逾時後查證、清理與主資料庫不變，再實作生命週期與 API，最後接 MES 和電商後台畫面。這是後續工作，不以目前 CI 交易測試取代展示功能。
